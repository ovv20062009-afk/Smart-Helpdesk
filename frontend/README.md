# ЛР 8. Форма Smart Helpdesk

Пользователь вводит номер, текст и канал обращения. Приложение отправляет запрос в REST API из ЛР 7, проверяет ответ и показывает тему, маршрут, оценку и источник. JSON вручную вводить не нужно. Модель и препроцессор остаются в сервере lab5.

[Отчёт](../docs/lab8_report.md), [архитектура](../docs/lab8_architecture.md), [протокол проверки](../docs/lab8_test_results.md).

## 1. Установка

Команды выполняются в Windows CMD из корня Smart-Helpdesk. Для интерфейса создаётся отдельное окружение. Его зависимости не нужно устанавливать в lab5/.venv: Streamlit 1.51.0 использует pyarrow 21.0.0, а проверки сервера закреплены на pyarrow 23.0.1.

```cmd
py -3.12 -m venv .venv-ui
.venv-ui\Scripts\python.exe -m pip install -r frontend\requirements.txt
.venv-ui\Scripts\python.exe -m pytest tests_frontend -q
```

При подготовке проверены Python 3.12, Streamlit 1.51.0, requests 2.32.4, pandas 2.2.3, NumPy 2.2.6, Pydantic 2.11.7, pyarrow 21.0.0 и pytest 8.4.2. Основные версии закреплены в frontend/requirements.txt.

## 2. Подготовка API

Нужен работающий сервер ЛР 7. Если контейнеры уже созданы, запустите их из любого каталога:

```cmd
docker start smart-helpdesk-lab7
docker start smart-helpdesk-lab7-fallback
curl.exe http://127.0.0.1:8000/ready
```

Основной /ready должен вернуть 200 и status=ready. У резервного контейнера /ready возвращает 503, потому что модель намеренно отключена. Это ожидаемое поведение. /health у обоих отвечает 200.

Для нового клонирования сначала выполните подготовку артефактов и сборку по lab5/README.md. Отдельно создайте локальные токены командой configure_local.py init. Если вместо Docker нужен запуск API в Python, из lab5 выполните:

```cmd
.venv\Scripts\python.exe configure_local.py serve
```

Сервер и интерфейс запускаются в разных терминалах. Не нужно одновременно занимать порт 8000 контейнером и Python-сервером.

## 3. Запуск формы

Из корня проекта:

```cmd
.venv-ui\Scripts\python.exe -m frontend.run_ui
```

Откройте http://127.0.0.1:8501. Оставьте учебный пример или введите своё обращение. Нажмите «Разобрать обращение».

Пример: номер T-8, текст «Не могу войти, забыла пароль», канал «Сайт». Ожидается TECHNICAL. Если оценка ниже 0.8, маршрут будет «Оператор» и появится просьба о ручной проверке. Это штатный результат.

run_ui.py явно читает APP_DEMO_TOKEN из локального lab5/.env и передаёт его только процессу Streamlit как API_TOKEN. Токен в форме не показывается. Значение не нужно копировать в браузер или JSON. Файл lab5/.env остаётся вне Git.

Для другой настройки можно задать API_URL и API_TOKEN в терминале. API_TOKEN имеет приоритет. Далее используется APP_DEMO_TOKEN из окружения, затем из lab5/.env. Адрес по умолчанию http://127.0.0.1:8000. Шаблон frontend/.env.example не читается автоматически. Если ранее задавали API_TOKEN вручную и хотите снова использовать локальный файл, очистите переменную командой `set API_TOKEN=`.

Прямой запуск тоже возможен, но требует заранее настроенных переменных окружения:

```cmd
.venv-ui\Scripts\python.exe -m streamlit run frontend/app.py --server.address 127.0.0.1
```

## 4. Контракт и поведение

| Поле формы | Поле API и проверка |
|---|---|
| Номер обращения | ticket_id, 1–100 символов, латиница, цифры, дефис, подчёркивание |
| Текст | text, 1–5000 символов, после очистки должны остаться слова или распознаваемый контакт |
| Канал | channel: web, email, chat |

Клиент вызывает POST /api/v1/predict с Bearer-токеном. Идентификатор в ответе должен относиться к отправленному обращению. Проверяются UUID4, обязательные поля, диапазоны чисел, отсутствие NaN/Infinity, UTC-время и согласованность источника, маршрута и ручной проверки.

Успех HTTP 200 ещё не означает корректный результат. Неверный JSON или противоречивый ответ показываются как ошибка интеграции, без карточки оценки.

Для model значение degraded должно быть false. Если текст неизвестен словарю, договорённость ЛР 7 допускает category=null и confidence=null с передачей оператору. Это не подменяется нулём.

Для fallback_rule обязательны degraded=true и confidence=null. Два разных слова одной категории позволяют правилу предложить отдел, одно слово оставляет проверку оператору. Поэтому резервный результат может предлагать IT_SUPPORT, но это не прогноз модели. Предупреждение остаётся заметным.

## 5. Ошибки и время ожидания

| Ситуация | Что видит пользователь |
|---|---|
| Нет локальной настройки токена | Не настроен доступ |
| 401 | Сервис не принял учётные данные |
| 403 | Клиенту запрещён разбор обращений |
| 422 | Сервер отклонил вход |
| 429 | Лимит исчерпан и подсказка Retry-After |
| 503 | Сервис не может подготовить результат |
| Отказ соединения | Не удалось подключиться к сервису |
| Таймаут | Сервис не ответил за отведённое время |
| Неверный ответ | Оценка не получена из-за ошибки формата |

Таймауты requests равны 3 секундам на соединение и 10 секундам на ожидание чтения. Это учебные значения для локального небольшого расчёта. Они не являются жёстким пределом всей операции. Таймаут клиента не доказывает остановку вычисления на сервере.

Автоматических повторов нет. Перенаправления HTTP также не выполняются. Retry-After показывается как подсказка сервера, без предположения, что это всегда целое число секунд. При новой попытке прежний результат очищается; неудачный запрос не получает старую успешную оценку.

## 6. История и CSV

В сеансе хранятся последние 100 попыток: время, номер, текст, канал, статус, доступный результат и безопасный код ошибки. В таблице на странице показаны основные колонки, а в CSV входят все поля истории. Для ошибки численная оценка пустая.

«Скачать CSV» выгружает файл UTF-8 с BOM для кириллицы. «Очистить историю» удаляет историю и текущую карточку. Перезапуск или завершение сеанса может потерять историю. Это не постоянная база обращений.

В CSV нет токена, Authorization и внутренних трассировок. Текстовые ячейки, похожие на формулу, получают начальный апостроф перед экспортом. Это учебная защита для открытия в таблицах, а не гарантия безопасности любых дальнейших преобразований файла.

Вводимый текст сохраняется в истории, поэтому для демонстрации нужны вымышленные обращения без персональных данных. История ручных обращений не является временным рядом оборудования.

## 7. Резервный режим и ручная демонстрация

Остановите интерфейс сочетанием Ctrl+C. Затем из корня:

```cmd
.venv-ui\Scripts\python.exe -m frontend.run_ui --fallback
```

Та же форма будет обращаться к резервному API на порту 8001. Для учебного примера ожидаются предупреждение о резервном режиме, отсутствие численной оценки и маршрут «Техническая поддержка». Перед этим контейнер smart-helpdesk-lab7-fallback должен работать.

Для проверки отказа соединения оставьте обычную форму открытой, выполните в другом терминале `docker stop smart-helpdesk-lab7` и отправьте новое обращение. Появится ошибка, а в истории останутся прежний успех и новая ошибка без оценки. Затем восстановите API командой `docker start smart-helpdesk-lab7`.

Для демонстрации неверного токена остановите интерфейс, в его терминале выполните `set API_TOKEN=invalid-local-test`, затем обычную команду запуска. После проверки остановите интерфейс, очистите переменную `set API_TOKEN=` и запустите снова. Настоящий секрет не выводится на экран.

Нужны четыре скриншота: штатный ответ, резервный режим, ошибка доступа или соединения, история. Токен и чувствительные тексты на них не включаются.

## 8. Воспроизводимая сквозная проверка

При работающих основном и резервном API из корня выполните:

```cmd
docker restart smart-helpdesk-lab7
.venv-ui\Scripts\python.exe -m frontend.verify_live
```

Скрипт использует Streamlit AppTest для отправки формы и настоящий HTTP для модели, ошибки доступа, резервного режима и квоты. Отдельно проверяется реальный отказ соединения с локальным портом без слушателя. Записываются docs/lab8/live_protocol.json, ответы и ui_history.csv. Это автоматическая проверка формы, а не ручная работа в браузере.

Скрипт намеренно исчерпывает квоту. После него дождитесь Retry-After либо перезапустите основной учебный API перед ручными запросами. Если сервер запущен без Docker, настройки API_URL и FALLBACK_API_URL позволяют выбрать другие адреса. Потребуется отдельный API с отключённой моделью для резервного сценария.

Таймаут и неверный JSON воспроизводятся в автоматических тестах с явной подменой. Реальный отказ GPU не проверялся: в проекте используется CPU-модель.

## 9. Проверки и сдача

При подготовке прошли 73 теста клиентского слоя и формы, линтинг, отдельный процесс Streamlit и сквозной сценарий AppTest с настоящим API. Результаты Linux сохранены в docs/lab8 и отмечены как подготовительные.

Обновлённый CI проверяет интерфейс в отдельном окружении и выполняет сквозной сценарий с контейнерами API. Статус Passing для нового коммита подтверждается после публикации. Успех ЛР 7 относится к предыдущей версии.

На Windows прошли 73 теста за 11.10 с и все шесть сценариев frontend.verify_live. В браузере проверены модель, остановка API, история и резервный режим. Четыре скриншота сохранены в docs/lab8, результаты описаны в [windows_checks.md](../docs/lab8/windows_checks.md). Перед сдачей остаётся проверить CI новой ветки. Ограничения: временная история, общий учебный токен, локальная квота одного процесса, искусственные данные, непроверенная калибровка и отсутствие внешнего развёртывания.
