# ЛР 5. Контейнеризация Smart Helpdesk

## Цель

Упаковать компонент классификации обращений в Docker и предоставить HTTP-интерфейс. Подготовить сборку с фиксированными зависимостями, проверкой готовности и автоматическими smoke-тестами.

## Связь с предыдущими работами

Сохраняется тема № 4 из ЛР 2: служба поддержки и маршрутизация обращений. В ЛР 3 проверялся словарный классификатор. В ЛР 4 созданы очищенные данные, train/test и обученный препроцессор TF-IDF.

ЛР 4 не сохраняла обученную модель классификации. Поэтому в ЛР 5 добавлен скрипт prepare_artifacts.py: он обучает LogisticRegression на готовых признаках train и оценивает результат на test. Препроцессор ЛР 4 не переобучается. Для работы сервиса используются два артефакта: preprocessor.joblib и model.joblib.

Пример телеметрии из методички заменён текстами обращений. В ЛР 5 после списка задач прямо указано, что дальнейший материал дан как пример. Отрицательному давлению из примера соответствует неверный вход нашей темы: пустой текст или недопустимый канал.

## Реализация сервиса

src/schemas.py описывает вход и выход. Запрос содержит ticket_id, text и channel. Pydantic отклоняет пустой текст, превышение длины, неизвестный канал и лишние поля с HTTP 422.

src/api.py реализует GET /health и POST /predict. При старте lifespan вызывает загрузчик, который проверяет версии библиотек, контрольные суммы, число признаков и классы модели. После успешной проверки оба артефакта сохраняются в app.state. При последующих запросах файлы не читаются.

Сначала сохранённый препроцессор преобразует текст и канал. Затем модель вычисляет вероятности категорий. Справочник связывает TECHNICAL с IT_SUPPORT, PAYMENT с FINANCE и STUDY с STUDENT_OFFICE. Если максимальная вероятность ниже 0.8, обращение передаётся оператору. Если словарь TF-IDF не узнал ни одного слова, отдел также не назначается.

В ответ включены версия модели v1.0.0 и версия препроцессора lab4-tfidf-v1. Числа confidence получаются из predict_proba; их калибровка и качество на реальных обращениях не проверялись.

Недоступные, повреждённые или несовместимые артефакты приводят к HTTP 503 на /health и /predict. Ошибка во время вычисления даёт HTTP 500 с общим сообщением. Реальные тексты обращений в журнал не записываются.

## Сборка образа

Dockerfile содержит две стадии на основе python:3.11-slim. В первой устанавливаются только библиотеки инференса. Файл requirements.txt копируется раньше исходников. Поэтому изменение кода не требует повторной установки тех же зависимостей.

Во вторую стадию переносятся установленные библиотеки, код и подготовленные артефакты. В образ не входят MLflow, Pandera, DVC, pytest и исходные CSV/Parquet. Пользователь контейнера имеет UID 10001. Uvicorn слушает 0.0.0.0:8000 внутри контейнера. HEALTHCHECK обращается к /health.

.dockerignore разрешает только необходимые файлы и исключает виртуальные окружения, data/raw, Git, DVC, кэши и .env. Контекст сборки задаётся папкой lab5. Dockerfile в корне репозитория относится к ЛР 2 и для этой работы не используется.

Образ имеет тег smart-helpdesk:v1.0.0. Команда запуска публикует порт только на локальном адресе компьютера: `-p 127.0.0.1:8000:8000`.

## Ответы на контрольные вопросы

1. Почему python:3.11-slim? Он уже содержит Python нужной ветки и меньше полного образа. В ubuntu пришлось бы отдельно устанавливать Python и его зависимости. Для используемых библиотек доступны готовые колёса, поэтому компилятор в рабочем образе не нужен.

2. Зачем отдельно COPY requirements.txt? Docker повторно использует слой установки библиотек, если requirements.txt и предыдущие слои не изменились. Изменение src не сбрасывает этот слой.

3. Что будет без -p? Сервис продолжит слушать внутри контейнера, но порт не будет опубликован на localhost компьютера. Запрос к localhost:8000 не попадёт в этот контейнер. EXPOSE только описывает порт и не публикует его.

4. Почему не latest? Этот тег не указывает конкретный выпуск: его можно передвинуть на другой образ. Тег v1.0.0 делает выпуск понятным. Для точного восстановления также фиксируют digest или ID образа, поскольку любой обычный тег технически можно изменить.

5. Что будет без .dockerignore? В контекст могут попасть окружение, датасеты, кэш и секреты. Это увеличит передачу и может привести к попаданию лишних файлов в слои. Само отсутствие .dockerignore не обязательно вызывает аварию, но делает сборку тяжелее и менее контролируемой.

6. Почему загрузка через lifespan? Чтение и проверка артефактов выполняются один раз на процесс. Запросы используют готовые объекты из app.state. Это уменьшает задержки и позволяет обнаружить проблему до обработки обращений. При нескольких процессах каждый загрузит собственную копию.
