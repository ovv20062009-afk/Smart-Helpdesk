# ЛР 7. REST API Smart Helpdesk

## Цель

Предоставить доступ к модели маршрутизации обращений через проверяемый REST API. Отделить сетевые обработчики, доступ, квоту и вычисление.

## Тема и связь с предыдущими работами

Продолжена тема № 4: служба поддержки и умная маршрутизация обращений. Исходники остаются в lab5. Методичка разрешает сохранить структуру существующего проекта. Модель и TF-IDF взяты из предыдущих работ, версия комплекта v1.4.0. Новая обученная модель для этой лабораторной не требуется.

Пример телеметрии адаптирован к текстовым обращениям. Вместо device_id используется ticket_id. Входные признаки: text и channel. Целевая переменная: TECHNICAL, PAYMENT или STUDY. Изменение темы проекта не выполнялось.

## Контракт

Обязательны ticket_id и text. Идентификатор: от 1 до 100 символов, латиница, цифры, дефис или подчёркивание. Текст: от 1 до 5000 символов, после очистки должны остаться слова. Канал может быть web, email или chat. Если его не передали, используется web; null не допускается. Лишние поля запрещены.

Ответ содержит trace_id и ticket_id, блок prediction с оценкой и маршрутом и блок metadata с версиями, UTC-временем, длительностью, источником и признаком degraded. UUID4 создаётся заново для каждого запроса. Он совпадает в теле ответа, X-Trace-ID и JSON-логе. Проверка ответа выполняется через Pydantic до отправки.

Оценка confidence берётся из predict_proba. Выбирается максимум по реальному model.classes_, а не условный второй столбец. Вектор вероятностей проверяется на размер, конечность, диапазон и сумму. Модель многоклассовая, отдельный положительный класс не выбирается. Калибровка не проверялась, поэтому оценка не называется гарантированной вероятностью правильности.

Порог модели 0.8 унаследован из учебного проекта. Если оценка ниже, обращение отправляется оператору. При неизвестных словах confidence=null и также нужна ручная проверка. Fallback использует отдельный порог двух разных слов одной категории без ничьей. threshold_used в ответе относится к модели, а не к подсчёту слов.

Старый /predict сохранён как deprecated, но использует те же проверки доступа и общую квоту. Обойти ограничения через него нельзя. Значение source=model сохранено из ЛР 6; в примере методички оно называлось ml_model.

## Значение HTTP-статусов

| Код | Семантика в проекте |
|---|---|
| 200 | /health отвечает либо получен валидный прогноз модели или явно отмеченный Fallback |
| 401 | Не установлен допустимый клиент; передаётся WWW-Authenticate: Bearer |
| 403 | Клиент распознан, но права на прогноз нет |
| 422 | Вход не соответствует схеме при корректном доступе |
| 429 | В скользящем окне нет свободных допусков; указан Retry-After |
| 503 | Не настроены токены, модель не готова на /ready либо недоступны оба способа расчёта |

/health показывает, что процесс отвечает. Даже без артефактов он возвращает HTTP 200, но сообщает degraded и фактический model_loaded. /ready возвращает 503 при отсутствующей модели, последнем сбое расчёта или ненастроенном доступе. При временном сбое следующий успешный модельный прогноз восстанавливает готовность.

Если модель недоступна, сохранённое резервное правило позволяет POST /api/v1/predict вернуть 200. Это не делает /ready успешным. Если сломано и правило, прогноз возвращает 503. Отсутствующая оценка не заменяется нулём.

## Доступ и квота

Токены находятся вне кода. configure_local.py init создаёт два случайных секрета в локальном .env, который игнорируется Git. Docker явно читает файл через --env-file, а запуск без контейнера выполняется командой configure_local.py serve. При старте настройки читаются один раз. Изменение токена требует перезапуска.

APP_DEMO_TOKEN соответствует клиенту helpdesk_demo с правом прогноза, APP_READONLY_TOKEN соответствует helpdesk_readonly без этого права. Сравнение выполняется secrets.compare_digest. Проверка can_predict реально вызывает 403. Отсутствие основного токена или совпадение токенов считается ошибкой настройки с 503.

Квота хранит моменты допусков известного client_id. Устаревшие записи удаляются по monotonic. Проверка и добавление выполняются под одной блокировкой. Отклонённый по квоте запрос не продлевает окно. Retry-After рассчитывается по времени самого раннего действующего допуска.

Квота относится к прохождению зависимости допуска. Невалидный запрос с корректным доступом может занять допуск, как и Fallback или последующий отказ вычисления. 401 и 403 не расходуют квоту. Оба адреса прогноза делят историю. Контроль состояния доступен независимо от квоты.

## Модель и ограничения вычисления

Модель и препроцессор загружаются один раз при запуске. Проверяются контрольные суммы, версии библиотек, число признаков и классы. Идентификатор обращения не используется как признак. Порядок признаков и преобразования сохранены из ЛР 4. На HTTP-запросе переобучение не выполняется.

Адаптер не импортирует FastAPI. Проверки доступа не размещаются в алгоритме классификации. Синхронный маршрут def подходит для библиотек scikit-learn. Вызов модели и запись её состояния защищены отдельным Lock. Это согласует общее состояние в одном процессе, но не обещает ускорение расчётов.

Тестовые подмены используются явно для ошибок и некорректных результатов. Сквозные запросы используют настоящие LogisticRegression и TF-IDF из сохранённых артефактов.

## Ограничения

Это учебный доступ с двумя постоянными токенами. Срок действия, ротация, полноценные учётные записи и HTTPS здесь не реализованы. История квоты теряется при перезапуске. Несколько workers имеют отдельную память. Произвольные неверные токены не создают новые записи в лимитере: учитываются только известные клиенты.

Квота допускает всплески и не ограничивает число долгих задач сама по себе. Блокировка модели в текущем варианте выполняет вычисления по одному на процесс; это простое учебное решение с ограниченной пропускной способностью. Общая квота кластера потребует внешнего хранилища.

Данные искусственные, тест содержит 12 обращений. Метрики модели не подтверждают качество на настоящих данных. Порог и Fallback требуют отдельной оценки перед практическим использованием.

## Контрольные вопросы

1. Чем модель отличается от API? Модель вычисляет категорию по признакам. API принимает HTTP-запрос, проверяет доступ и вход, вызывает вычисление и оформляет ответ.

2. Почему проверки формы не заменяют сервер? Запрос можно отправить без формы, например через curl. Поэтому окончательная проверка всегда выполняется на сервере.

3. Чем отличаются 401, 403 и 422? При 401 клиент не установлен. При 403 он установлен, но действие запрещено. При 422 вход не соответствует схеме.

4. Что считает квота? Допуски известного клиента за последние 60 секунд. Это не только успешные прогнозы; допущенный запрос может закончиться 422, Fallback или ошибкой расчёта.

5. Почему workers не делят словарь? Это отдельные процессы со своей памятью. Общий словарь Python не становится распределённым хранилищем.

6. Чем частота отличается от параллелизма? Частота показывает число запросов за интервал. Параллелизм показывает число одновременно выполняемых задач. Квота 60 в минуту допускает отправку всех 60 почти сразу.

7. Почему /health и /ready отвечают по-разному? Процесс может работать и обслуживать Fallback, хотя модель отсутствует или последний её расчёт сломан. Поэтому liveness 200 не означает readiness 200.

8. Как проверить окно без ожидания? Передать лимитеру управляемую функцию часов, изменить время в тесте и проверить допуск ровно на границе окна.

9. Почему score не всегда вероятность? Число из predict_proba зависит от модели и данных. Без проверки калибровки нельзя считать 0.8 гарантией, что 80% таких решений верны.

10. Что сохранять при замене модели? Схему входа и ответа, смысл категорий, порядок признаков, совместимые преобразования, правила маршрутизации и обозначение источника. Версии и Model Card нужно обновить, тесты и оценку качества повторить.
