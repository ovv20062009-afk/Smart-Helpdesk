## JSONL и trace_id

Для каждого HTTP-запроса middleware создаёт новый UUID4. Один trace_id используется в теле /predict, заголовке X-Trace-ID и записи request_complete. Этот механизм действует и для ошибок 422. Параллельные запросы получают разные UUID и не смешивают записи.

Одна строка лога является одним JSON-объектом. Он содержит время, уровень, имя логгера и событие. Для запроса добавляются trace_id, код HTTP, источник решения и длительность. Данные отправляются через StreamHandler в sys.stdout. Uvicorn использует тот же JSONFormatter; стандартный access-log отключён, чтобы не дублировать запросы и не записывать query-параметры.

В логи не включаются исходный текст, тело запроса, Authorization и traceback. При сбое записывается только имя класса исключения. Поля extra_data ограничены разрешённым списком. Ошибка валидации возвращает тип, поле и сообщение без копии введённого значения.

В lab5/docs/lab6/http_model_response.json и http_model_logs.jsonl сохранён один проверенный HTTP-сценарий. Для резервного режима есть отдельные файлы http_fallback_rule_response.json и http_fallback_rule_logs.jsonl. UUID из ответа найден в соответствующем логе скриптом check_json_logs.py.

## Fallback

Модель и препроцессор читаются один раз при старте через lifespan. Если артефакты отсутствуют, повреждены или модель падает во время predict_proba, запрос автоматически обрабатывается резервным правилом. То же происходит при ошибке преобразования и некорректных вероятностях.

Правило считает разные ключевые слова по трём категориям. Два и более совпадения одной категории без ничьей позволяют предложить её отдел. Одно слово, повтор одного слова, ничья и отсутствие совпадений оставляют решение оператору.

| Сценарий | Результат |
|---|---|
| Модель работает | source=model, вероятность из predict_proba |
| Модель отключена, «Не могу войти, забыла пароль» | source=fallback_rule, TECHNICAL, IT_SUPPORT, confidence=null |
| Модель отключена, «пароль оплата» | source=fallback_rule, OPERATOR, ручная проверка |
| Неверный вход | HTTP 422; резервное правило не вызывается |
| Временный сбой исчез | Следующий запрос снова использует модель |

При активном резервном режиме /health имеет HTTP 200 и status=degraded. Дополнительно видны model_loaded и fallback_available. Это показывает, что сервис отвечает, но ML-модель не готова. Резервный результат не маскируется под прогноз модели.

Переменная HELPDESK_DISABLE_MODEL=1 предусмотрена для демонстрации отказа. Она не меняет артефакты и не добавляет публичный административный эндпоинт.

## CI/CD

Пайплайн запускается при push в main и ветки feature, а также при Pull Request в main. Последовательно выполняются установка зависимостей, линтинг, тесты прежних компонентов, проверка контрактов ЛР 4, подготовка данных и модели, тесты API и отказоустойчивости. Затем собирается образ с тегом полного SHA коммита.

В CI поднимаются два временных контейнера: обычный и с отключённой моделью. Для обоих запускаются smoke-тесты, проверяется OpenAPI и валидность JSONL. После успешных проверок образ сохраняется в tar.gz и передаётся через артефакт GitHub Actions вместе с Model Card. Это доставка проверенного образа и тестовое развёртывание. Внешний рабочий сервер не настраивался, его адрес и учётные данные в задании не заданы.

Ошибки тестов или сборки блокируют передачу образа. Проверочные результаты сохраняются отдельно. Контейнеры CI удаляются в завершающем шаге даже при ошибке.

## Ответы на контрольные вопросы

1. Чем синхронный REST отличается от очереди? При REST клиент ждёт результат в том же запросе. Очередь позволяет принять задание и получить результат позже. Универсальной границы в секундах нет: важны тайм-ауты клиента и прокси, допустимая задержка и число одновременных задач. Долгие расчёты, выходящие за эти ограничения, стоит выполнять через очередь.

2. Зачем trace_id? Он связывает ответ, событие Fallback и запись завершения запроса. При большой нагрузке можно найти конкретный запрос по одному идентификатору, а не искать похожие строки по времени. Это помогает отличать параллельные обращения.

3. Чем JSONL лучше произвольного текста? Поля можно разбирать, фильтровать и агрегировать без сложных шаблонов. Elasticsearch или Loki смогут искать по trace_id, source и status_code. Каждая строка является отдельной записью.

4. Как работает Fallback? Защитный блок ловит сбой модельного этапа и вызывает заранее проверенное простое правило. Для нашей задачи это позволяет продолжить сортировку или передать обращение оператору. HTTP 200 допустим, потому что резервный сценарий предусмотрен контрактом и явно указан в source. Для задач без безопасного резервного решения правильнее отказ или ручная проверка, а не произвольный ответ.

5. Зачем Model Card? Он описывает версию, назначение, данные, оценку и ограничения модели, чтобы результат нельзя было использовать вне проверенной области по ошибке. Пять разделов этой работы: Model Details, Intended Use, Factors & Data, Metrics & Evaluation, Caveats & Limitations.

6. Почему при редких авариях важен Recall? Если 99% записей без аварий, прогноз «аварий нет» даст 99% Accuracy и пропустит все аварии. Recall покажет долю найденных настоящих аварий. Его рассматривают вместе с Precision, иначе можно получить слишком много ложных тревог. В нашем проекте аналогично оцениваются отдельные категории обращений.
