# ЛР 3. Компонент маршрутизации обращений

Проект: Smart Helpdesk. Репозиторий: https://github.com/ovv20062009-afk/Smart-Helpdesk

## Что сделано

Из архитектуры ЛР 2 выбран компонент, который получает обращение и предлагает отдел. Его можно запускать прямо из Python, без FastAPI и базы данных. В `app/ml/component.py` отдельно описаны вход, классификация и правило выбора отдела. Подготовка текста берётся из общего `app/ml/preprocessing.py`.

Вход: `ticket_id` от 1 до 100 символов и `text` от 1 до 5000 символов. Пустой текст и лишние поля вызывают ошибку Pydantic. Выход: категория или `None`, отдел или `None`, флаг ручной проверки, версия алгоритма и слова, по которым принято решение. Если словарь классификатора отсутствует, возникает `ModelUnavailableError`. Ошибка не превращается в успешный прогноз.

Алгоритм ищет слова из трёх словарей: технические вопросы, оплата, учёба. Для автоматического маршрута нужны два разных слова одной категории без ничьей. Одно слово, ничья или отсутствие совпадений приводят к ручной проверке. Числовой вероятности здесь нет: словарь не умеет оценивать вероятность. Справочник отделов применяется после классификации. Он не отправляет сообщение сотруднику, а только предлагает маршрут.

Тестовые фразы придуманы для работы, реальные обращения и личные сведения не использовались. Файл модели из сети не загружается.

## Запуск

Из корня проекта в PowerShell:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m pytest -q tests/test_component.py
.\.venv\Scripts\python.exe -m app.ml.demo
```

## Проверка

| Вход | Ожидаемый результат |
|---|---|
| «Не могу войти, забыла пароль» | TECHNICAL, IT_SUPPORT, ручная проверка не нужна |
| «Оплата прошла, нужна квитанция» | PAYMENT, FINANCE, ручная проверка не нужна |
| «Забыла пароль» | TECHNICAL, отдела нет, проверяет оператор |
| «Пароль и оплата» | Спорная категория, отдела нет, проверяет оператор |
| Пустая строка | Ошибка входного контракта |
| Отсутствует словарь | Явная ошибка ModelUnavailableError |

## Что изменилось по сравнению с ЛР 2

В ЛР 2 пример API использует заглушку с условными числами confidence 0.7 и 0.9. В этом локальном компоненте вместо такого числа возвращаются совпавшие слова. Поэтому решение можно объяснить и проверить. При будущей интеграции с API понадобится согласовать выходной контракт и заменить старую заглушку. Нельзя считать количество совпадений вероятностью.

Ограничение: слова проверяются буквально. Неизвестные формулировки и формы слов могут уйти на ручную проверку. Качество на настоящих заявках не измерялось. В дальнейшем можно собрать размеченные и обезличенные обращения, обучить модель и проверить её на отдельной выборке.

Цель работы достигнута: отдельный компонент принимает и проверяет обращение, классифицирует его, предлагает маршрут и явно обрабатывает ошибку зависимости.

## Результаты запуска

Проверка выполнена локально на Windows, Python 3.12.2.

Команда проверки:

    .\.venv\Scripts\python.exe -m pytest -q tests/test_component.py

Результат: 8 passed in 0.49s. Все восемь проверок прошли.

Команда демонстрации:

    .\.venv\Scripts\python.exe -m app.ml.demo

| Пример | Фактический результат |
|---|---|
| «Не могу войти, забыла пароль» | TECHNICAL, IT_SUPPORT, ручная проверка не нужна |
| «Оплата прошла, нужна квитанция» | PAYMENT, FINANCE, ручная проверка не нужна |
| «Забыла пароль» | TECHNICAL, отдел не выбран, требуется человек |
| Пустой текст | Ошибка входа: текст пустой |

Во всех трёх успешных ответах указана версия алгоритма keywords-1.0. Результаты демонстрации совпали с ожидаемыми.

## Место компонента в архитектуре

Компонент реализует классификацию и выбор маршрута из раздела 3 архитектуры ЛР 2. Для локальной проверки эти действия объединены в HelpdeskComponent. Подготовка текста используется из общего модуля app/ml/preprocessing.py.

Компонент запускается отдельно. API и аудит из ЛР 2 пока используют прежнюю реализацию. Подключение нового компонента к API оставлено для следующих работ.
